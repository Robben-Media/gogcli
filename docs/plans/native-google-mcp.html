Native Google MCP

Give agents typed Google tools backed by direct API calls. Optimize completed workflows for speed, correctness, and useful results. Keep language and code-reuse choices subordinate to those measurements.

Owner: Robben Media project maintainer, with the primary agent responsible for integration. Baseline: e81e585, release v0.10.0. This document is the authoritative MCP migration plan. It defines the intended behavior and rollout gates. The local implementation evidence section records progress; no server has been deployed.

Business posture

The desired path is agent → MCP server → Google APIs. Tool execution must not spawn gog, invoke a shell, parse terminal output, or depend on loading a CLI instruction skill. Go is the proposed runtime because it supports inexpensive concurrent I/O, persistent connection pools, and a deployable binary. No language-level speed advantage over alternatives has been measured for these workloads.

Success means the same representative work finishes correctly with fewer avoidable agent round trips and no material latency regression. A shorter tool list, faster empty request, or lower token count alone is insufficient.

  • Deliver a useful read-only vertical slice first: email retrieval, Drive/Docs lookup, Calendar lookup, and GA4/Search Console/Sheets reporting.
  • Support multiple connected Google accounts from the first release, including personal Gmail and Google Workspace. The user-facing setup is browser OAuth sign-in for each account, with no service-account key or per-account Cloud project.
  • Add deliberate write operations after identity, policy, and retry behavior pass tests. Existing Google credentials remain outside the repository and outside model context.
  • Build a parity ledger for implemented CLI operations. Migrate remaining operations by actual consumer need. The 588-method API-gap backlog in the existing specs is not an MCP implementation commitment.
  • Publish workflow instructions with the service where clients support them. Replace local skill installation only after the receiving client proves it can discover and activate those instructions.
  • Retain existing CLI consumers and administrative authentication commands during migration. CLI retirement is a consumer-by-consumer outcome, not a prerequisite for native MCP.

Current execution boundary: local implementation, fixture verification, and independent review of the packages below. Production endpoints, profile changes, live sends, shared-document edits, and CLI removal are later rollout actions with named targets and verification.

Security posture

Security control: existing OAuth and service-account plumbing, secret storage, and persisted command policies provide reusable building blocks. Their CLI behavior does not establish correctness inside a concurrent server.

Security control: policy is currently applied in internal/cmd/policy_enforcement.go. Native handlers must use a shared policy evaluator before acquiring data or issuing an API request. Directly calling current handlers would bypass their normal entry-point checks.

Accepted risk: this plan records no new acceptance of data exposure or unsafe writes. Compatibility limits and provisional performance targets remain engineering decisions to verify.

Required controls

  • Derive the caller from trusted startup configuration for stdio or validated server authentication for HTTP. MCP client names, request metadata, and tool arguments are not authenticated identities.
  • Bind each caller to allowed Google accounts, OAuth client buckets, and operations. Every Google tool requires an account_id obtained from the caller-filtered account catalog. Selection narrows this grant; it never widens it. Reject unknown accounts, guessed email addresses used as authority, and ambiguous defaults.
  • Keep Google OAuth credentials separate from MCP client authentication. Do not pass client-supplied Google bearer tokens through to arbitrary upstream endpoints.
  • Apply existing policy specificity and deny semantics consistently, then intersect them with the MCP server's explicit operation allowlist. Hidden tools must also be denied when invoked by name.
  • Keep credentials, content, and private resource IDs out of routine logs. Record operation, opaque principal identifier, elapsed time, upstream call count, error category, and trace identifier.
  • Default to bounded reads. Enable write tools through trusted configuration. Tool annotations describe behavior; server authorization enforces it.
  • Make downloads explicit and size-bounded. Start with text/metadata tools; later binary transfers use authenticated, expiring handles or MCP resources, not arbitrary filesystem paths or unrestricted URLs.
  • Rewrite MCP workflow examples without embedded account-specific credentials, shell grants, or automatic updater instructions. Preserve user-edited local skills until a verified replacement is in use.

C4 container

Use one Go binary, provisionally cmd/gog-mcp. A transport adapter converts MCP requests to typed operations; operation code calls Google's Go clients directly. Shared policy and authentication live below both interfaces. One process supports multiple user-connected accounts. Each request resolves a permitted account_id to an immutable account/client identity; there is no process-global active account. A profile can be restricted to only work, only personal, or an explicit set of accounts. Do not introduce a queue, remote cache, or microservices for the read-only pilot; reuse protected local credential storage and a minimal account registry.

Google OAuth and multiple accounts

User requirement: connecting personal Gmail and Workspace must feel like signing into a normal Google integration. The product owns OAuth application setup once. Users connect their accounts through Google's browser consent screen; they do not create service-account JSON keys, enable domain-wide delegation, or create a Cloud project per mailbox.

  1. Provide a small account-management page with "Connect Google account", the connected account list, granted capabilities, reconnect, and disconnect. Connecting another account uses Google's account chooser and adds a connection without replacing the previous one.
  2. Configure an app-owned Google Cloud project with an External OAuth audience so both consumer Gmail and Workspace accounts are eligible. Enable the required APIs there. Use appropriately registered desktop/loopback or web OAuth clients for the deployment; never embed a confidential web-client secret in downloadable frontend code.
  3. Use authorization code flow with state bound to the initiating user, exact redirect validation, PKCE where supported, and verified Google identity. Derive the account from verified provider data, not an email typed by an agent. Bind records to the stable Google subject and retain verified email and a user-editable display label.
  4. Request offline access and store each account's refresh token in the existing protected store. Never return tokens through MCP. Reuse an existing refresh token when Google's response omits a new one; persist rotations safely. Normal access-token expiry refreshes automatically.
  5. Request permissions by capability. The read-only email pilot needs Gmail read access; sending/drafts and other services require their appropriate additional scopes. Check scopes actually granted and prompt to extend access when necessary. An OIDC sign-in alone does not grant mailbox access.
  6. Expose accounts_list as a local metadata tool returning only connections granted to the caller, their stable account IDs, labels, and capability status. Every Google tool uses the selected ID. Replies and writes retain the selected mailbox identity; never fall back to another account after an error.
  7. Implement reconnect and disconnect. Revoke the affected app grant where appropriate, evict its token/client caches, and remove its local connection while preserving other accounts. Revocation must clearly describe whether it affects other deployments using the same Google grant.

Google OAuth application credentials and service-account keys are different. The application still needs a one-time OAuth client configuration; that belongs to deployment administration, not mailbox onboarding. The existing CLI already has user OAuth code to adapt, but new explicitly OAuth-connected accounts must not be silently overridden by an existing service-account configuration.

The connection registry holds the opaque account ID, stable Google subject, verified email, label, owning principal, OAuth client reference, explicit auth_mode=oauth, actual granted scopes, update time, and credential generation. Keep refresh tokens in the protected store, which already separates tokens by client and email. Adapt legacy records explicitly instead of changing their account/client association. An optional future service-account mode requires its own explicit configuration and is not part of Gmail onboarding.

Plan a production-ready OAuth consent configuration. Google's External apps in Testing generally receive refresh tokens that expire after seven days for these scopes. Gmail read access is a restricted scope, so publishing/verification requirements must be checked for the actual deployment and audience. Workspace administrators can restrict third-party applications. These are deployment gates; do not present a weekly re-consent test setup as finished sign-in support.

Request, result, and performance contract

  1. Validate typed inputs and resource syntax; resolve the permitted account/client; authorize the canonical action; establish the request deadline; acquire bounded quota/concurrency capacity.
  2. Use cached clients and token sources keyed by account, OAuth client, credential mode, scopes, and credential generation. Share safe connection pools. A cached token source must not retain the first tool request's cancelable context.
  3. Issue Google calls with the current request context. Bound fan-out, page sizes, fetched bytes, and total duration. Use API field masks and summary views before introducing response caching.
  4. Return typed structured content and an explicit next-page token. Include account alias, source IDs/links as appropriate, date range/timezone, truncation, freshness, and partial failures where relevant. Output schema must match actual results.
  5. Map errors to actionable categories: invalid input, forbidden operation, authentication required, insufficient Google scope, not found, quota exhausted, deadline exceeded, upstream failure, and unknown write outcome. Avoid leaking raw secrets or treating partial success as full success.

Use metadata/token caching first. Any later data cache must have an account-bound key, documented freshness, refresh behavior, and invalidation after writes. Never share mail, Drive content, or reporting results across callers just because their query text matches.

Open the secret store at controlled startup, with a clear noninteractive error on failure. The existing keyring timeout helper explicitly assumes a short-lived CLI; do not repeatedly leak its blocked goroutines inside a server. Test rotated refresh-token persistence without overwriting unrelated token metadata. Define explicit cache invalidation after credential changes and an atomic policy snapshot/reload path; do not silently retain revoked grants indefinitely.

P0 gives every operation an explicit retry class: safe_read, provider_keyed_write, or non_replayable_write. Pass this classification to the API layer through typed call options, not a guessed HTTP method. Read-only POST operations such as reporting can be safe to retry. Unknown operations fail closed to no automatic replay. If shared transport changes affect CLI writes, document and test that intentional behavior change.

For a write without a Google-supported idempotency mechanism, an ambiguous failure returns outcome_unknown, retryable=false, and reconciliation guidance. Test both transport and host behavior: the MCP client must not replay that tool automatically on 429, disconnect, or a generic error. Neither MCP request IDs nor email Message-ID headers guarantee deduplication. A local receipt cannot make a remote side effect exactly-once after a crash.

Before enabling a write, require the intersection of authenticated caller account grant, trusted server operation enablement, applicable policy, and any action-specific approval required by the host/user. A model-supplied confirmation flag grants nothing. Keep any circuit breaker deliberately scoped per account and upstream service, or disable it initially; one failing mailbox must not block unrelated accounts.

Protocol, skills, and client compatibility

The current 2026-07-28 protocol removes protocol sessions and the initialization handshake. The official Go module proxy publishes v1.8.0; its tagged README lists support for this revision and older clients. Pin and exercise that released SDK rather than implementing the wire protocol ourselves.

The Skills extension is Final, but the implementation list still marks Go SDK support as in progress. Core MCP support does not establish Skills extension support.

  • Publish concise tool descriptions and optional standard resources/prompts first. These support instruction retrieval but do not claim automatic native skill activation.
  • Add skills/list, skills/get, manifests/digests, and resource reads only through a verified implementation of the released extension. Prefer a released SDK; if unavailable, evaluate a narrow adapter and its conformance cost before scheduling it.
  • Advertise only implemented capabilities. A client that cannot activate MCP skills must still use the core tools without requiring a CLI skill.
  • Keep the tool catalog stable for an authorized principal/configuration. Progressive discovery, tool search, and code-mode composition depend on the host; a server alone cannot promise those benefits.

Verification and acceptance

Representative workflows

  1. Find recent client emails and retrieve the relevant thread with correct account, message order, and content.
  2. Find a client document, extract the requested facts, and return source IDs/links with honest truncation.
  3. Find calendar availability over a DST boundary without treating all-day events or partial calendar errors as free time.
  4. Read a GA4 report and Search Console query for the same requested reporting period; preserve their different metric meanings and timezone/date conventions.
  5. Read a sparse spreadsheet range and compute a checkable summary. Later, update a designated test sheet with a bounded write and verified readback.

Measurement design

  • Compare baseline CLI plus its existing instructions with native MCP using the same model, reasoning setting, task wording, data fixtures, output requirements, and concurrency. Measure discovery/skill loading as part of end-to-end work.
  • Separate cold startup, warm tool overhead, Google latency, token-refresh events, and total task completion. Compare stdio with HTTP on the same machine before adding fleet network distance.
  • Use deterministic fake Google endpoints for repeatable server timings and failures. Use paired live read-only trials later to establish real behavior; mocks do not prove Google latency or account authorization.
  • Record p50/p95 latency, upstream request count, retries, prompt/output tokens, agent tool calls, peak memory, and task correctness. Include failure and recovery outcomes, not just successful calls.
  • For microbenchmarks collect enough repeated samples to show variance, initially 100 warm calls and 20 cold starts per case. For agent evaluation begin with at least 10 paired runs per workflow and randomize order. These are screening runs; gather at least 50 paired runs for any workflow whose p95 drives acceptance, and more if variance leaves the result inconclusive. Keep live API volume bounded and respect quotas.
